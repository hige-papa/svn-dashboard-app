## 1. ログイン・アカウントに関するQ&A

### Q1-1: ログインしようとすると「ユーザーが見つかりません」と表示されます

**A:** 入力したメールアドレスがTascalに登録されていない可能性があります。以下を確認してください。
- メールアドレスのスペルが正しいか（大文字/小文字の区別はありません）
- 管理者にアカウントが作成されているか確認してください
- アカウント作成時と異なるメールアドレスを使用していないか確認してください

### Q1-2: パスワードを何度入力しても「パスワードが間違っています」と表示されます

**A:** 以下を確認してください。
- Caps Lockがオンになっていないか
- パスワードに前後の空白が含まれていないか
- 最近パスワードを変更していないか

解決しない場合は、サインイン画面の「パスワードを忘れた方はこちら」からパスワードリセットを実施してください。

### Q1-3: ログイン直後に自動でログアウトされてしまいます

**A:** アカウントのステータスが **inactive**（無効）に設定されている場合、ログイン後にシステムが自動的にログアウトします。管理者に連絡して、アカウントの再有効化（active への変更）を依頼してください。

### Q1-4: パスワードリセットメールが届きません

**A:** 以下を確認してください。
- 迷惑メールフォルダを確認してください
- メールアドレスが正しく入力されているか確認してください
- Firebase Authenticationからのメール（noreply@...firebaseapp.com）が受信拒否になっていないか確認してください
- 数分待っても届かない場合は再度送信してください

### Q1-5: 複数のブラウザ・端末から同時にログインできますか？

**A:** はい、可能です。Firebase Authenticationは複数端末からの同時ログインに対応しています。ただし、一方の端末でアカウントが無効化された場合、全端末でログアウトされます。

### Q1-6: パスワードの要件はありますか？

**A:** Firebase Authenticationの標準仕様として、パスワードは6文字以上である必要があります。セキュリティのため、英数字と記号を組み合わせたパスワードの使用を推奨します。

### Q1-7: viewer権限ではどこまで操作できますか？

**A:** viewer権限のユーザーは以下の操作が可能です。
- カレンダーの閲覧（全ビュー）
- ユーザー・施設・設備・チーム・部署の一覧・詳細表示
- Wiki記事の閲覧
- 自分のプロフィール確認

以下の操作はできません。
- 予定の登録・編集・削除
- マスターデータの作成・編集
- 管理者メニューへのアクセス

## 2. カレンダーに関するQ&A

### Q2-1: 週次ビューで他のユーザーの予定が見られるのに、月次ビューでは自分の予定しか見えません。なぜですか？

**A:** これは仕様です。
- **週次ビュー**: チーム全体のスケジュール調整が主な用途のため、全ユーザーの予定を表示します
- **月次・日次ビュー**: 個人のスケジュール管理が主な用途のため、ログインユーザーの予定のみ表示します

他のメンバーの予定を確認したい場合は、週次ビューに切り替えてください。

### Q2-2: カレンダーの表示が遅いです

**A:** 以下をお試しください。
1. **初回アクセス**: 最初のデータ読み込みは最大3秒程度かかります。これは正常な動作です
2. **2回目以降**: マスターデータ（ユーザー、祝日など）はキャッシュされるため、約1.5秒に短縮されます
3. **改善しない場合**: ブラウザのキャッシュをクリアしてリロードしてください
4. **ネットワーク環境**: VPN接続時やネットワークが不安定な場合、読み込みが遅くなる場合があります

### Q2-3: 予定を登録した後、カレンダーに戻ると違う週が表示されています

**A:** 通常はカレンダーの表示位置が自動的に保存・復元される仕組みになっています。もし復元されない場合は以下をお試しください。
- ブラウザの「戻る」ボタンではなく、サイドバーのカレンダーリンクから遷移している場合、保存された位置が適用されないことがあります
- ブラウザのlocalStorageがクリアされると位置情報も失われます

### Q2-4: 祝日がカレンダーに表示されません

**A:** 祝日は管理者が手動で登録する必要があります。国の祝日が自動で反映されるわけではありません。管理者に祝日の登録を依頼してください。

### Q2-5: 週次ビューで特定のユーザーだけ表示したい

**A:** 週次ビューのユーザーフィルター機能を使用してください。表示したいユーザーのみ選択し、それ以外を非選択にすることで絞り込めます。

### Q2-6: 過去のカレンダーデータはいつまで遡れますか？

**A:** Firestoreにデータが保存されている限り、制限なく過去の予定を閲覧できます。日付ナビゲーション（◀ボタン）や日付ピッカーで過去日に移動してください。

## 3. 予定登録に関するQ&A

### Q3-1: 予定のコンフリクト（重複）が検出されましたが、そのまま登録できますか？

**A:** はい、コンフリクト検出は警告のみで、登録をブロックしません。会議室のダブルブッキングなど、意図しない重複がないか確認のうえ、問題なければそのまま登録できます。

### Q3-2: プライベート予定を設定すると、他のメンバーからはどう見えますか？

**A:** プライベートに設定された予定は、**参加者以外**のユーザーからは以下のように表示されます。
- タイトル: 「予定あり」（本来のタイトルはマスクされます）
- 説明: 非表示
- 参加者・施設・設備: 非表示

参加者として登録されたユーザーには、通常通りすべての情報が表示されます。

### Q3-3: 予定に参加者を追加したいのですが、一覧にいないユーザーがいます

**A:** 以下の原因が考えられます。
- ユーザーアカウントがまだ作成されていない → 管理者にユーザー登録を依頼してください
- ユーザーのステータスが inactive になっている → 管理者にアカウントの有効化を依頼してください
- マスターデータのキャッシュが古い → ブラウザをリロードしてください

### Q3-4: 予定を複製（コピー）できますか？

**A:** はい、予定詳細画面の **「コピー」** ボタンから予定を複製して登録画面に遷移できます。元の予定の内容がフォームにプリセットされるので、変更したい部分だけ修正して登録できます。

### Q3-5: 終日予定は登録できますか？

**A:** 現在、Tascalでは時刻付きの予定のみ対応しています。終日予定を登録する場合は、開始時刻を9:00、終了時刻を18:00など業務時間帯全体を指定して登録してください。

### Q3-6: 施設や設備を予定に紐付ける意味は？

**A:** 施設・設備を予定に紐付けることで以下のメリットがあります。
- **コンフリクト検出**: 同じ施設・設備が同時間帯に別の予定で使われていないか自動チェックされます
- **リソース管理**: 週次ビューで「どの会議室がいつ使われているか」を把握できます
- **予定の詳細情報**: 予定詳細画面で使用する施設・設備を確認できます

## 4. 繰り返し予定に関するQ&A

### Q4-1: 繰り返し予定を登録すると、何件分の予定が作成されますか？

**A:** 終了条件によって異なります。
- **終了なし**: 1年分の予定が自動生成されます
- **日付指定**: 指定した終了日までの予定が生成されます
- **回数指定**: 指定した回数分の予定が生成されます
- **上限**: ハードリミットとして20年分を超える予定は生成されません

### Q4-2: 繰り返し予定の1件だけ時間を変更したい

**A:** 以下の手順で対応してください。
1. 変更したい日の予定をクリックして詳細画面を開きます
2. 「編集」ボタンをクリックします
3. 時間を変更して保存します

ただし、現在の仕様では個別の予定を編集すると、その予定のみが変更されます。同一グループの他の予定には影響しません。

### Q4-3: 繰り返し予定を「これ以降すべて削除」した場合、再度作成し直す必要がありますか？

**A:** はい。「これ以降の予定」を削除した場合、削除された予定は復元できません。必要に応じて新しい繰り返し予定を作成してください。

### Q4-4: 毎月第3月曜日のような繰り返し予定は作れますか？

**A:** はい、繰り返しパターンで「毎月」を選択し、月次タイプで「毎月第N曜日」を選択することで設定できます。

### Q4-5: 繰り返し予定の間隔をカスタマイズできますか？（例: 2週間おき）

**A:** はい、「カスタム」パターンを使用して間隔を指定できます。例えば2週間おきの場合、パターンを「毎週」にして間隔を「2」に設定してください。

## 5. 勤怠管理に関するQ&A

### Q5-1: 勤務形態を登録し忘れた日がありますが、過去の日付でも登録できますか？

**A:** はい、過去の日付の勤務形態も登録・変更可能です。日付範囲を指定して過去日を表示し、勤務形態を設定してください。

### Q5-2: 他のメンバーの勤務形態を確認できますか？

**A:** はい、勤怠管理画面では指定した期間内の**全ユーザー**の勤務形態・ランチ参加・夕食参加状況を一覧表示できます。

### Q5-3: ランチ参加状況はどこで使われますか？

**A:** ランチ参加状況は以下の用途で使用されます。
- ランチシャッフル機能での参加者リストの参考情報
- チーム全体の出社状況やランチ参加予定の把握
- 食事の手配人数の把握

### Q5-4: 勤務形態を一括登録できますか？（例: 今週は毎日出社）

**A:** 現在、一括登録機能はありません。日付ごとに個別に設定する必要があります。

## 6. Wikiに関するQ&A

### Q6-1: Markdown記法がわかりません

**A:** EasyMDEエディタにはツールバーが付いているので、Markdownの記法を知らなくてもボタン操作で見出し、太字、リスト、リンクなどを挿入できます。よく使う記法は以下の通りです。

```
# 見出し1
## 見出し2
**太字**
*斜体*
- リスト項目
1. 番号付きリスト
[リンク](URL)
```

### Q6-2: Wiki記事を間違えて削除してしまいました。復元できますか？

**A:** 記事のバージョン履歴が保存されています。ただし、記事自体を削除した場合は復元が困難です。管理者に相談してFirestoreのバックアップからの復旧を検討してください。

### Q6-3: 下書き（draft）の記事は他のユーザーに見えますか？

**A:** 記事ステータスが「draft」の記事も、現在の仕様では一覧画面に表示される場合があります。完全に非公開にしたい場合は、記事を作成せずに手元で下書きを管理することを推奨します。

### Q6-4: Wiki記事にファイルを添付できますか？

**A:** 記事本文中にMarkdown形式で画像リンクを埋め込むことは可能です。ただし、ファイルの直接アップロード機能は現在のバージョンでは提供されていません。

### Q6-5: 記事のバージョン履歴はどこで確認できますか？

**A:** 記事詳細画面でバージョン履歴を確認できます。記事を更新するたびにバージョン番号がインクリメントされ、更新前のスナップショットが保存されます。

## 7. ランチシャッフルに関するQ&A

### Q7-1: シャッフル結果が他のユーザーの画面にも即座に反映されますか？

**A:** はい、ランチシャッフルのデータはFirestoreのリアルタイムリスナーで同期されるため、シャッフルを実行すると全ユーザーの画面にリアルタイムで結果が反映されます。

### Q7-2: 20名以上でシャッフルできますか？

**A:** 現在の仕様では参加者リストは固定20枠のため、20名が上限です。20名を超える場合は、グループを分けて複数回シャッフルすることを推奨します。

### Q7-3: チーム分けの人数は変更できますか？

**A:** チーム分けは3〜4名を基本として自動最適化されます。現在のバージョンではチームサイズの手動指定はできません。

### Q7-4: 過去のシャッフル結果を確認できますか？

**A:** ランチシャッフルのデータは最新の結果のみ保持されます（1件のドキュメントを上書き）。過去の結果を残したい場合は、結果をスクリーンショットやメモとして保存しておくことを推奨します。

## 8. マスターデータ管理に関するQ&A

### Q8-1: 施設のステータスを「maintenance」にすると予定はどうなりますか？

**A:** ステータスを「maintenance」に変更しても、既に登録済みの予定は自動的に削除されません。ただし、新規予定登録時にメンテナンス中の施設を選択するとコンフリクト検出の対象になります。メンテナンス期間中の既存予定については、手動で変更・削除を行ってください。

### Q8-2: ユーザーを削除できますか？

**A:** Tascalではユーザーの完全削除は推奨していません。代わりにステータスを **inactive** に変更することで、そのユーザーはログインできなくなり、実質的に無効化されます。これにより過去の予定データの整合性が保たれます。

### Q8-3: 部署の変更をしたい場合、ユーザーに紐付いている部署情報はどうなりますか？

**A:** 部署マスターを変更しても、ユーザーの部署情報は自動更新されません。部署名が変更になった場合は、該当ユーザーのプロフィールも個別に更新する必要があります。

### Q8-4: チームにメンバーを追加・削除する方法は？

**A:** チーム編集画面（`/team/[id]/edit`）で、メンバーの追加・削除が可能です。ユーザーマスターから選択する形式で操作できます。admin権限が必要です。

### Q8-5: CSVインポート/エクスポートはどのデータに対応していますか？

**A:** メンテナンス画面（`/maintenance`）からFirestoreの各コレクションに対してCSVインポート/エクスポートが可能です。エクスポートファイルはBOM付きUTF-8のCSV形式で、Excelでそのまま開くことができます。

## 9. パフォーマンス・キャッシュに関するQ&A

### Q9-1: ブラウザをリロードするとデータの読み込みが遅くなるのはなぜですか？

**A:** ブラウザをリロードするとメモリ上のキャッシュ（マスターデータ等）がクリアされるため、Firestoreからデータを再取得する必要があります。初回読み込みは約3秒程度かかりますが、2回目以降はキャッシュにより約1.5秒に短縮されます。

### Q9-2: データが古いまま表示されている気がします。更新する方法は？

**A:** 以下の方法で最新データに更新できます。
1. **ブラウザリロード**: ページ全体を再読み込みします（全キャッシュがクリアされます）
2. **自動更新を待つ**: マスターデータのキャッシュは10時間、日別オプションは1時間で自動的に再取得されます
3. **イベントデータ**: カレンダーの週移動やビュー切り替えを行うと、該当範囲のイベントが再取得されます

### Q9-3: 複数のタブでTascalを開いても大丈夫ですか？

**A:** はい、複数タブでの利用は可能です。ただし以下の点にご注意ください。
- タブ間でキャッシュは共有されません（各タブで独立したメモリキャッシュ）
- 一方のタブでデータを更新しても、他のタブには即座に反映されません（リロードが必要）
- ランチシャッフルはFirestoreのリアルタイムリスナーで同期されるため、タブ間でも即座に反映されます

## 10. セキュリティに関するQ&A

### Q10-1: Tascalのデータは安全ですか？

**A:** 以下のセキュリティ対策を実施しています。
- **通信暗号化**: すべての通信はHTTPS（TLS 1.2以上）で暗号化されます
- **認証必須**: Firebase Authenticationにより、認証済みユーザーのみアクセス可能です
- **データ暗号化**: Google Cloudのデフォルト暗号化（AES-256）でデータが保護されています
- **XSS対策**: Wiki記事のHTML表示にはDOMPurifyによるサニタイズ処理が適用されます
- **権限制御**: admin/user/viewerの3段階の権限でアクセスを制御しています

### Q10-2: プライベートイベントの情報が漏洩する心配はありますか？

**A:** プライベートイベントのフィルタリングはクライアント側で実施されるため、Firestoreに保存されたデータ自体にはイベントの全情報が含まれています。ただし、Firestoreへのアクセスは認証済みユーザーに限定されており、画面上では参加者以外にはマスク表示されます。

### Q10-3: 退職者のアカウントはどうなりますか？

**A:** 管理者がユーザーのステータスを **inactive** に変更することで、そのユーザーはログインできなくなります。退職者が登録した過去の予定データはそのまま保持されるため、予定の履歴確認に支障はありません。

## 11. 運用・保守に関するQ&A（管理者向け）

### Q11-1: 新入社員のアカウントを作成する手順は？

**A:** 以下の手順で作成します。
1. admin権限でログインします
2. ユーザー一覧画面（`/users`）を開きます
3. **「新規ユーザー」** ボタンをクリックします
4. 必要な情報を入力します
   - コード（社員コード）
   - 名前
   - メールアドレス
   - 初期パスワード
   - 部署
   - 権限（通常は user）
   - ステータス（active）
5. **「ユーザーを作成」** ボタンをクリックします
6. Firebase AuthenticationとFirestoreの両方にアカウントが作成されます
7. 新入社員にメールアドレスと初期パスワードを通知し、初回ログイン後にパスワード変更を促してください

### Q11-2: 祝日データを登録する手順は？

**A:** 以下の手順で登録します。
1. admin権限でログインします
2. 祝日管理画面（`/holiday`）を開きます
3. 日付と祝日名を入力して追加します
4. 年始に1年分の祝日をまとめて登録することを推奨します

**注意**: 国の祝日は自動反映されません。毎年、祝日データを手動で登録する必要があります。

### Q11-3: Firestoreのデータ使用量が心配です。コストはどれくらいですか？

**A:** Firebase Blazeプラン（従量課金）を使用していますが、以下の無料枠があります。

| サービス | 無料枠 |
|---------|--------|
| Firestore 読み取り | 50,000件/日 |
| Firestore 書き込み | 20,000件/日 |
| Firestore ストレージ | 1 GB |
| Cloud Storage | 5 GB |
| Authentication | 50,000 MAU |

社員100名以下の小規模利用であれば、無料枠内で運用可能な見込みです。Firebase コンソールで利用量を定期的に確認してください。

### Q11-4: デプロイの手順を教えてください

**A:** 以下の手順でデプロイします。

```bash
# 1. 依存パッケージのインストール
npm install

# 2. 静的サイト生成
npx nuxi generate

# 3. Firebase Hosting へデプロイ
firebase deploy --only hosting

# 4. Cloud Functions へデプロイ（必要な場合）
firebase deploy --only functions

# 5. Firestoreルール/インデックスのデプロイ（必要な場合）
firebase deploy --only firestore
```

### Q11-5: Firestoreのインデックスが不足していると言われます

**A:** `firestore.indexes.json` にインデックス定義が含まれています。以下のコマンドでデプロイしてください。

```bash
firebase deploy --only firestore:indexes
```

エラーメッセージにインデックス作成のURLが含まれている場合は、そのURLをクリックしてFirebaseコンソールからインデックスを作成することもできます。

### Q11-6: イベントキャッシュ（Cloud Storage）のデータが不整合を起こした場合は？

**A:** Cloud Functionsの `onEventChangeRecalculateCache` が自動的にキャッシュを再生成しますが、手動で再生成する場合は以下の手順です。
1. Cloud Functions の `initialCacheGeneration` をHTTPリクエストで呼び出します
2. これにより全イベントから週別キャッシュファイルが一括再生成されます

### Q11-7: ユーザーの権限をadminからuserに変更するには？

**A:** 以下の2か所で変更が必要です。
1. **Firestoreのusersコレクション**: ユーザー編集画面（`/users/[id]/edit`）で権限をuserに変更
2. **Firebase AuthenticationのCustom Claims**: Firebase Admin SDKまたはFirebaseコンソールでadminクレームを削除

Firestoreの権限だけ変更してもCustom Claimsが残っている場合、IDトークンの更新までadmin権限が維持される場合があります。

### Q11-8: データのバックアップはどうなっていますか？

**A:** 以下のバックアップ体制です。
- **Firestore**: Google Cloudの自動バックアップ機能により保護されます
- **フロントエンド**: ソースコードはGitリポジトリで管理されているため、再ビルド・再デプロイで復旧できます
- **認証データ**: Firebase Authenticationのマネージド管理により保護されます
- **RTO（目標復旧時間）**: 1時間以内（再デプロイ）
- **RPO（目標復旧時点）**: Firestoreの自動バックアップ頻度に依存

## 12. 障害対応に関するQ&A（管理者向け）

### Q12-1: 画面が真っ白になり何も表示されません

**A:** 以下の順序で確認してください。
1. **ブラウザのコンソール**: エラーメッセージを確認します
2. **ネットワーク**: Firebase各サービスへの接続が正常か確認します
3. **Firebase Hosting**: Firebase コンソールでHostingのステータスを確認します
4. **ビルドの問題**: 最新のデプロイが正常に完了しているか確認します

### Q12-2: Firestoreへの接続ができないエラーが発生しています

**A:** 以下を確認してください。
- **Firebaseプロジェクトのステータス**: Firebase コンソールでサービスの稼働状況を確認します
- **Google Cloud Statusダッシュボード**: 東京リージョン（asia-northeast1）の障害情報を確認します
- **Firestoreセキュリティルール**: ルールが正しく設定されているか確認します
- **ネットワーク**: ファイアウォールやプロキシで `firestore.googleapis.com` へのアクセスがブロックされていないか確認します

### Q12-3: Cloud Functionsのエラーが発生してカレンダーキャッシュが更新されません

**A:** 以下の手順で対処します。
1. Firebase コンソール → Functions → ログを確認します
2. Google Cloud Logging でエラーの詳細を確認します
3. メモリ不足の場合: Functions の設定でメモリを増量します（現在: 1GB）
4. タイムアウトの場合: Functions の設定でタイムアウトを延長します（現在: 300秒）
5. 手動復旧: `initialCacheGeneration` をHTTPリクエストで呼び出してキャッシュを再生成します

### Q12-4: 「WebSocket connection to 'ws://localhost:4000/ws' failed」というエラーが出ています

**A:** これはNuxt Contentモジュールの開発専用機能による**無害なエラー**です。
- アプリケーションの機能・パフォーマンスに影響はありません
- ユーザーには見えません（開発者ツールのコンソールのみに表示）
- 対応不要ですが、気になる場合は `nuxt.config.ts` で本番環境のWebSocketを無効化できます

### Q12-5: 大量のFirestoreクエリが発行されていてコストが増加しています

**A:** 以下を確認してください。
1. **loadDataの重複呼び出し**: composableとページの両方からloadDataが呼ばれていないか確認します
2. **watchの重複定義**: currentDateやcurrentViewに対する複数のwatchがないか確認します
3. **キャッシュの動作確認**: ブラウザコンソールで `[Cache] Hit` ログが出力されているか確認します
4. **Firestoreプロファイラ**: `printFirestoreDebugSummary()` でクエリ統計を確認します

期待されるクエリ回数:
- 初回ロード: 3〜4クエリ
- キャッシュ有効時の週移動: イベントクエリのみ（マスターデータはキャッシュヒット）

### Q12-6: 特定のユーザーだけログインできないという報告があります

**A:** 以下を確認してください。
1. **ステータス確認**: Firestoreの `users` コレクションで該当ユーザーの `status` が `active` であることを確認
2. **認証確認**: Firebase コンソール → Authentication で該当ユーザーのアカウントが存在するか確認
3. **パスワード**: パスワードリセットを実施してもらう
4. **ブラウザ**: 別のブラウザやシークレットモードで試してもらう
5. **キャッシュ**: ブラウザのキャッシュ・Cookieをクリアしてもらう
